## What changed

- `room.go(id)` in `internal/script`:
  - It records the destination through the new `Host.Go`, and the move happens when the hook ends.
  - `Thread.moved` makes waiting in a dialog after the call a script error.
  - Every hook's player argument now has `player.room`.
- `internal/game`:
  - `after()` applies the move through `enterLocked(room, moved)`, and the client first gets an `items` message with the new room's items.
  - A move that cannot start is refused, and the player stays where they were.
  - A player keeps the script instances of their last 4 rooms (`MaxRoomInstances`).
  - One message can make at most 4 moves (`MaxMoves`).
- The test pack has a cellar for the Playwright test.
- Docs: `docs/lua-sandbox.md`, `docs/websocket-protocol.md`, `docs/admin-limits.md`.

## Findings

security-reviewer (report only): 0 critical, 0 high, 2 medium, 2 low.

| Severity | Finding | Fix |
| --- | --- | --- |
| Medium | A move went half through when the new room could not start (Lua time used up, network or world full): the player was in the new room, its `on_enter` never ran, and a full network could trap the player | The new room's instance starts before the player moves; when `on_enter` is refused for time, the move is undone; errors before the move leave the player where they were |
| Medium | Every visited room kept an instance for the session, so one player walking a large pack could fill the memory share of a whole class's address | Only the last 4 rooms entered keep their instances; the admin doc says what that costs |
| Low | A chain of moves could hold the world lock for about 11 hooks' time and send 11 × 100 outputs | At most 4 moves per message; the Lua budget still stops a chain once used up |
| Low | The docs promised more than the code did | Rewritten after the fixes |

test-engineer (tests only) wrote edge, eviction, concurrency and fuzz tests in `internal/script/move_edge_test.go`, `internal/game/move_edge_test.go` and `internal/game/instances_test.go`. It found two bugs in the first eviction code:

| Bug | Fix |
| --- | --- |
| A refused move still counted as entering the room, so an older room outlived it | The visit order is restored when a move is undone |
| A refused move evicted an older room's instance anyway | The new instance starts first; the victim goes only after it started, and the memory check counts what the victim frees |

security-reviewer re-review: the four findings hold (the lock hold is down to at most 5 hooks per message, about 1 s at the default limits). New:

| Severity | Finding | Fix |
| --- | --- | --- |
| Medium | When the new instance started but its `on_enter` was refused for time, the undone move left that instance outside the visit order, so it was never evicted: repeated, one player passed the 4-instance cap up to the address's whole share | An undone move frees the instance it started, and the room that would give way is freed only once the move happens; `victim` also falls back to any other instance. `TestUndoneMovesKeepNoInstance` repeats the move 30 times |
| Low | The docs pointed to `state.player` before it exists | Marked as T-0023, the next change |

The gap noted before the re-review (an undone move had already evicted an older room) is closed by the same fix.
